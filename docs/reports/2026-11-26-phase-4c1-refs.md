# Phase 4c-1 gate: element refs and the imperative commands they enable (spec 070 §2)

This phase gives MAUI apps WinUI's element refs and what they're for: focusing from code, scrolling
to an element, WebView commands and navigation control, and the Entry cursor and selection. PR #16,
stacked on #15.

## What changed

- **Design (spec 070 §2).** Reviewed in four rounds by both model families before code. The rounds
  changed the design substantially:
  - ref ownership is recorded on the engine's node, so a failed update can't leave a ref on a dead
    view;
  - a scroll bridge that is correct through direct layouts;
  - list cells retire their tree when unbound;
  - three owner decisions (below) replaced state machines that kept producing new races.
- **Refs.** `ElementRef<T>` (`T : IView`), `UseElementRef<T>()`, `TypedElementRef.Create<T>()`,
  `.Ref(...)` and `UseElementFocus()`, with WinUI's names, in WinUI's `Microsoft.UI.Reactor.Input`
  namespace.
  - The engine binds a ref after mount or update. It releases the ref on unmount and on every failure
    path, only while the ref still points at that view.
  - A Controls-typed ref makes that element a Controls view on the direct registry. A wrong-typed ref
    is an error naming both types. Direct views can be focused.
  - Nothing moves to the shared core: WinUI's `ElementRef.Current` is a shipped `FrameworkElement`
    property, and the engines bind refs differently.
- **`UseElementFocus()`.** Added because Android can't focus from a new tree's first effect.
  - Direct views wait for their handler, then for joining a window: Android's attach event, and on
    iOS and Mac Catalyst a check that backs off to once a second. That check holds the view weakly,
    so a discarded tree can still be collected.
  - A request made off the UI thread goes through the render queue.
- **Scrolling.** `ScrollToAsync(ElementRef<T>, position, animated)`.
  - An all-Controls chain uses MAUI's own overload.
  - Any other chain sums frames through direct layouts and runs MAUI 11's own position calculation,
    insets included.
  - Its task completes `true` only when the scroll is at the target. It completes `false` when
    another request supersedes it, a handler is replaced or removed, the dispatch throws, or the
    scroll is still off target at a bound above the platform's animation length.
  - Any `ScrollView` gets this, including one Reactor didn't create.
- **WebView.** `OnNavigating` can cancel; a throwing callback cancels and is reported. `OnNavigated`
  now passes MAUI's `WebNavigatedEventArgs` (a breaking change to a preview API), posted so
  `CanGoBack` is current. `Url` loads when its declaration changes.
- **Entry.** `CursorPosition`, `SelectionLength` and `OnSelectionChanged`, with WinUI's semantics.
  - A declared value is written when it changes.
  - Each change is reported once, from the selection the platform actually shows.
  - Reactor's own writes are never reported.
  - A `MaxLength` truncation still reaches `OnTextChanged`.
- **Also fixed:** a list cell whose item is cleared left its tree mounted; it now unmounts.
- **Docs:** spec 070 §2 with its as-built record and per-platform characterization (§2.15), spec 068
  rows (Entry, WebView, ScrollView and RefreshView, focus, element refs), spec 065, the README, and
  the CHANGELOG.

- **Characterization first.** Device fixtures measured each platform before the behaviour was
  fixed. They covered: focus from a first effect, selection writes, input-type changes, overlapping
  scrolls, the animation length, interrupted scrolls and WebView cancellation. The fixtures assert
  the measured results.
- **Mutation checks:** 37 in the build (36 killed, 1 equivalent), 24 in the first review round
  (all killed except one equivalent), and 18 in the second (all killed).
- **CI's iOS WebView failures** came from the test code, not the product. Each failure was
  investigated to its mechanism:
  - **First head:** the page-load wait accepted a load from an earlier show. It now waits for a load
    after its own show.
  - **Later head:** the first page timed out after 10 s. On a cold simulator, WebKit's log shows its
    WebContent and GPU processes taking 6.4 s to launch, which put the first load at 8.4 s locally
    (later loads take 0.5–2.5 s). Both callbacks still fire. The first page in the app now waits up
    to 60 s with a message naming the cause. Later pages keep 10 s. Every load's time is recorded,
    and a timeout lists every event.

## Review

`pr-review` ran 7 dimensions on Claude plus a gpt-6.1-sol cross-check, then three rounds verifying the
fixes with both families. Security found no vulnerability; packaging found only a docs gap.

- **High, all fixed and confirmed by the other family** (each reproduced by gpt-6.1-sol with a
  headless probe first):
  - the bridge completed its task inline, so a continuation's new scroll was finished early;
  - MAUI's replay of a request parked before the handler counted as a second animation, which could
    leave a task pending;
  - replacing one handler with another stranded the task.
- **Medium, fixed:**
  - "always completes" didn't hold for a `ScrollView` Reactor didn't create, nor for a request
    that never got any finish (now bounded);
  - selection tracking swallowed a `MaxLength` truncation from `OnTextChanged`;
  - the README claimed a refused navigation is reported as cancelled;
  - direct-view focus gave up silently after 2 s;
  - an orientation change could confirm an unreached target;
  - test oracles that passed when nothing happened (WebView refusals, selection sequences, the inset
    gate, finish counts, zero-origin geometry).
- **Low, fixed:**
  - a late finish after a settle could settle the next request;
  - iOS focus polling kept a discarded tree alive;
  - a negative cursor threw on the Controls entry;
  - doc comments, global-usings docs and a culture-sensitive allow-list sample.

## Decisions for the gate

1. **Refs stay per renderer**, with WinUI's names; nothing moves to the shared core. Recommendation:
   accept.
2. **Entry selection follows WinUI and isn't controlled:** a declared value is written when it
   changes and isn't restored after user input. Three design rounds showed controlled selection
   can't be made sound on Android's deferred, split notifications, and no port needs it.
   Recommendation: accept.
3. **No URL deduplication.** `Url` is the requested source and loads when it changes; the docs tell
   apps to keep the current page in separate state. Recommendation: accept.
4. **`OnNavigated` passes `WebNavigatedEventArgs`** (breaking the preview `Action<string>`), so apps
   see cancelled and failed results. Recommendation: accept.
5. **The `ScrollView` element renders a subclass**, so an implicit `ScrollView` style needs
   `ApplyToDerivedTypes`. Recommendation: accept; documented.

## Open issues and follow-ups

- **To file in dotnet/maui:**
  - MAUI's own `ScrollToAsync` can leave a superseded call pending forever;
  - Android loses the page when it cancels a reload or back;
  - after a refused `GoBack`, Android reports the next script navigation as `Back`.
- **Reactor.Maui's trim analyzer is off.** MAUI's build targets disable it unless
  `_MauiDoNotConfigureTrimAnalyzer` is set (found by the packaging review). This predates this
  phase.
- **WinUI may lose a ref moved between siblings in one render.** Its update path clears a ref without
  checking who owns it, so a ref moved from a later sibling to an earlier one in the same render
  probably ends `null`. This is unconfirmed and will be checked with a WinUI unit test.
- **The upstream allocation test may be flaky** (see CI).
- **Spec number collision:** upstream `main` now has `067-table-driven-modifiers.md`, so the fork's
  067 to 070 are renumbered at the next upstream merge.
